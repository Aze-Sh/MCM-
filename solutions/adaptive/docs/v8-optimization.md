# v8 提速方法与同输入对比

更新：2026-09-12。当前算法标识为 `20260912-shared-service-r4`，主程序在 [`suanfa.py`](../python/near_optimal/suanfa.py)。当前默认仍是v7，v8通过 `--v8` 选择。

**已经取得实测提速，但“稳定比v7少500秒”尚未完成，也没有证明接近原题理论最优。** 四个开发固定案例全部更快，三个超过500秒；前轮八个验证案例全部更快、五个超过500秒。保留的八个混合源验证案例中，七个更快、五个超过500秒，一个Q4退步约184秒。以下同时列出未达标结果。

用户确认截图中的v7成绩为Q3 2966.25秒、Q4 7426.42秒，对应要求为2466.25秒、6926.42秒以内。截图对应的案例编码和原始日志尚未取得，因此本文的合成场景不能代替这两场演练的直接核验。本轮仅使用仓库内的离线模拟器，未连接官方模拟器或运行正式测试。

## 一、为什么原来的v8慢

原实现主要有三项损耗：搜索布局有冗余；很多源各自走到第二测量点；跨任务排序只看最近两个事件，源只定位一半就可能改去另一区域。

另一个容易忽略的问题在覆盖证书：旧Q4的25点布局确实能覆盖，但4096节点、深度12的计算预算不足以在该实现中证明它。某个案例因此在正常搜索结束后追加了完整备用搜索，时间从约8147秒增加到17367秒。预算用尽表示“尚未证明”，不能等同于“区域没有覆盖”。

## 二、当前算法逐步怎样做

### 1. 用更少的搜索站承担未知频道任务

Q3使用中心加六个半径1125米的环形点。Q4使用21点：中心、半径998米的8个等角点，以及半径1868米的12个等角点，外环从15度开始。

Q4的这组坐标通过有理数连续覆盖核查；不是仅在离散网格上抽查。证明使用5013个节点，最大深度12，当前执行预算为20000节点、深度14。外环可以在源域之外，源域限制的是干扰源的位置。

Q4必须覆盖可能的发射朝向。对于任意合法源位置，距它1000米以内的测点需要在几何上围住它，使任意闭180度发射半平面至少包含一个测点。七个全向覆盖点不满足这项定向要求，不能拿来代替Q4搜索。

### 2. 多个源共用第二观察点

一次搜索会逐个测量仍未知的频道。如果同站发现至少三个只有一次正观测的源，程序提出一个共同的第二观察点，而不是让每个源分别安排一段移动。

候选点位于当前位置350米外，每30度一个候选。评分同时考虑绕行距离和各源预计减少的径向不确定性。若旧方向与新视线夹角为 `alpha`，测角误差为 `epsilon`，预测宽度近似为

`min(旧宽度, 2 × epsilon × 距离 / |sin(alpha)|)`。

这只是挑选测量位置的启发式。真正更新可行域时，仍使用接口返回的完整角度误差区间；Q4也可能返回无信号，此时不会伪造方向。每次实际测量都计费、扣除必要的试探额度，并检查备用预算。

例如同站发现9个源，机器人只走一次350米，再换频道完成9次测量。它仍需支付9次测量费用，节省的是重复移动。

r4对Q4进一步估计候选点实际能接收的概率。它使用该频道已经取得的全部正、负观测，包括发现前的无信号记录。剩余责任块的面积与中心提供有限个位置代表；对每个代表位置，把半径1000～1500米按观测距离分段，并计算允许的发射朝向区间。正观测要求接收点位于发射半平面内，半径范围内的负观测要求接收点位于半平面外；全向模型则必须同时符合所有距离条件。

全向与定向各占一半的先验权重、均匀半径和均匀朝向，都是评分模型的假设，题设并未给出这些分布。位置用有限代表近似，因此不能把估计概率说成真实概率、严格后验或最坏情况保证。模型无法形成有效权重时返回0.5，仍只影响可选动作。

Q4对每个源使用 `接收概率 × 预计定位收益 − 6秒`，只测净收益为正的频道；整批净收益还必须超过350米观察点带来的绕行费用，否则取消这次额外移动。Q3保留r3做法。取消补测不取消未知频道搜索，也不会给任何频道凭空写入无信号证据。


### 3. 用后验区间决定下一次推进位置

取得第二个正观测后，当前可行多边形通常已经给出有效的径向下界。程序将多边形投影到最近观测的方向轴上，得到 `[lo, hi]`，下一次推进取这个区间的中点，横向偏移由区间宽度决定。

例如距离已经缩到500～600米，下一步应围绕550米安排，而不是继续把距离当成0～600米、退回300米处测量。候选点本身不构成证据，后续真实观测才会缩小可行域。

Q3还把初次发现的源域与题设1800米圆域的保守24边外包相交，剔除原正方形四角的不可能区域。半平面含三角函数误差外扩，保证保留整个合法圆域。这个变体在Q4的开发测试中有明显回退，所以当前Q4保留原有源域表示。

### 4. 对全部当前任务一起安排顺序

每个未清除源是一项任务，每个尚需搜索的站也是一项任务。源任务可以有多个模式：不同的实际RF入口，或已经通过几何核查的清除点。

每个模式包含入口、预计服务时间和预计出口。一个计划的估值为：从当前位置走到首任务入口的费用，加各项服务费用，以及前一出口到下一入口的费用。

`anpai_renwu` 比较多个完整初始顺序，再做两轮单任务插入。每个候选顺序由 `pinggu_shunxu` 用动态规划重新选择各任务模式，不能把一个来源不明的“虚拟源中心”当作机器人的测量入口。选定源后持续处理到清除成功，再回到全局排序，减少跨区域反复往返。

**预计出口取可行域中心，服务时间也是排序估计；这不是严格的全局耗时上界。** 实际预算保护使用另一套保守的完整备用费用。把服务图做更深的精确优化曾降低图内估值，却提高真实总时间，因而没有采用该实验分支。

### 5. 在已经到达的位置顺路补测

完成一次搜索或一次源清除后，程序检查其它已知源：视差是否至少0.25、预计不确定性减少能否抵消6秒测量及换台费用，并排除已经实际测过的位置。

Q3允许可行域中心距当前点不超过1000米的候选，不再要求整个可行域都能接收；同时限制正、负观测合计少于3次。无信号也能结合原正观测缩小可行域。Q4仍要求整个可行域在999米以内、正观测少于3次，并把上节的估计接收概率计入预计收益；这个距离条件不保证发射朝向可见，所以仍允许无信号。

满足条件就站在原地补测，不增加移动。预计收益只用于选动作，实际返回值才作为证据。Q3放宽接收条件后，两固定案例分别再省31.482秒和11.810秒。继续放开测量次数、或在每个RF中间停点都补测，出现收益不一致，未采用。

### 6. 避免重复测已经确认无信号的点对

Q4出现过这样的循环：同一源的两个测点都已返回无信号，但双阴性几何核查没有缩小当前区域；下一轮又选择完全相同的两个测点，直到轮数上限。对静态源重复同频道、同位置的阴性测量没有新信息，却仍需付费和来回移动。

`bimian_chongfu` 在全局选择和源内部选择之后检查真实阴性记录。若点对两点均已确认无信号，就改为已有完整光学续接的首动作；后续仍检查事件预算、真实响应和剩余责任。它不把“没有新信息”解释为“源不存在”。

旧验证Q4 16源案例有56次重复阴性RF，本修复省384.650秒，其中测量费280秒、移动92.650秒、失败清除费12秒；固定Q4 10源案例省120秒。重复动作问题消除了，但源入口、出口和后续服务费用的预测误差仍然存在。

### 7. 小区域直接用完整光学链清除

Q4内部定位会比较继续RF测量与2～8个光学点组成的完整排查链。程序沿当前方位轴及其垂直方向尝试铺点；只有横向宽度足够小、且点数不超过8时才提出候选。

每条候选都做连续几何核查：按距离最近的光学点把当前可行多边形分成Voronoi片区，用有理数半平面裁剪构造每一片，并检查整片都在对应点的19.8米圆内。题目光学清除半径为20米，这里留出计算余量。有限位置代表只用于比较预计首次成功成本，完整区域的覆盖证明才承担不漏源的保证。

程序比较正序、逆序和按单位费用预计清除权重生成的顺序。若预计首次成功成本低于继续RF的乐观估计，就执行整条链的成功前缀。选择前检查完整事件预算和足够的有限额度；每个点都真实调用清除接口，成功即停，失败就更新剩余责任。不得用代表点都被覆盖来替代连续覆盖证书，也不得把预计费用当作严格上界。

本轮组合在10场Q4性能对照中有9场比r3更快，平均省239.913秒；旧validation 16源一场比r3慢54.131秒。这是采用该组合的实际权衡，仍未满足所有场景比v7少500秒。

## 三、全清条件如何保持

20个频道分别保留真实观测，不能共享阴性证据。所有已发现源必须收到清除成功响应；剩余频道必须由实际观测证明不存在，或者由已经发现16个源的数量上限排除。找到10个源本身不能停止。

每个接受动作都减少实际搜索/光学责任，或者消耗不会重置的有限试探额度。预算不足、无法证明完成或候选无法继续时，仍执行原49点搜索与固定光学责任链。规划中的未来测量只能用来比较候选路线，不能提前写成阴性证据。

初始完整备用的保守费用仍约41638.717虚拟秒。真实截止时间的保证仍依赖实际请求延迟与机器运行条件，不能承诺任意网络故障下都能完成。

日志增加覆盖预算和 `geometry_version`。新Q3使用几何版本2，Q4使用版本1；缺少字段的历史日志按旧几何和旧证明预算回放，防止新几何改变旧日志的任务减少记录。

## 五、复核方式和剩余工作

在仓库根目录执行，全部是离线操作：

```bash
python scripts/check_repository.py --suite all
python experiments/near-optimal/benchmark.py --suite matched --output /tmp/mcm-v8-matched
python experiments/near-optimal/benchmark.py --suite validation --output /tmp/mcm-v8-validation
python experiments/near-optimal/benchmark.py --suite validation --algorithm v7 --output /tmp/mcm-v7-validation
python experiments/near-optimal/benchmark.py --suite fresh --output /tmp/mcm-v8-fresh
python experiments/near-optimal/verify_results.py --results experiments/near-optimal/results/optimization-20260912/round4 --require-current-policy
```

给Q4的既定RF点对按接收概率调整先后顺序也做了额外对照：原六场略有收益，但保留四场两快两慢、平均仅省0.434秒，因此没有增加到当前代码。

后续Q3实验也未替换r4：按下一入口微调清除点收益很小且有回退；把后续服务入口加入共享测量候选，使六场中的四场变慢；有证书地滑动首个搜索站没有改善固定案例。允许连带调整两个相邻搜索站，十场只有一场省24.227秒，其余不变。用三个假设世界模拟后续策略、再选择共享观察点，两固定例反而慢60.191和39.885秒。原型与日志已经归档，见[实验记录](../../../docs/flow/v8-faster-than-v7.md)和[原型文件校验清单](../../../experiments/near-optimal/results/optimization-20260912/trials37-41-manifest.json)。这些实验没有改动当前主程序及其验证结果。

再次检索本地结果后，仍未找到截图对应的案例编码或原始v7记录。下一步需要这两场输入，先确认相同布局、误差规则、v7代码版本和计时口径，再核验Q3不超过2466.25秒、Q4不超过6926.42秒。单独的总时间和源数不足以重建案例；原动作日志可以核对计时与策略，但只有观测轨迹时也未必能还原全部源参数。

当前成果应视为有验证依据的改进版。剩余问题是：Q3部分案例尚未省足500秒，Q4新增混合源场景仍有回退，截图演练尚缺同案例输入；同时，当前排序对未来发现和后续服务时间的预测仍偏粗，不能把小模型的最优值或启发式评分解释为原问题理论最优。

2026-09-13提交前合并了远端Windows离线模拟兼容修复，主策略保持r4。两项超时测试通过；重跑四个固定案例后，虚拟用时及727条实际请求与原记录一致。提交前核验材料见 [publish-20260913](../../../experiments/near-optimal/results/publish-20260913/README.md)，Windows运行方法见 [Windows说明](windows-v8.md)。
